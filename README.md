# Job application database

SQLite CRUD helpers for validated job and resume content.

- Database operations ensure the schema bundled beside the Python module exists.
- `insert_job(mapping)` and `insert_resume(mapping)` validate complete `Job` and
  `Resume` content. Nested values are serialized into their individual SQL
  columns. Top-level fields without SQL columns are rejected; nested extra
  fields inside JSON sections remain supported.
- Omitted IDs and timestamps are generated by SQLite; omitted resume
  `successful` values default to `0`. Explicit values, including nulls, are
  preserved rather than replaced by defaults.
- Both insert helpers return the inserted text `id`, not SQLite's numeric
  rowid. The `jobs put` and `resumes put` commands print that ID, so it can be
  captured and used for subsequent reads or foreign-key links. An explicitly
  supplied null ID remains null and returns `None`; omit IDs for generation.
- `read_job(id)` and `read_resume(id)` use the shared row decoders to decode
  JSON columns and return record models.
  SQL IDs, timestamps, and resume `successful` values are authoritative;
  there is no whole-record `item_json` column.
  Missing records raise `LookupError`.
- Low-level CRUD helpers restrict table and column identifiers to the schema.
  Foreign keys are enabled on every connection. Deleting a job referenced by a
  resume raises `sqlite3.IntegrityError`; delete its resumes first.

Each decorated operation commits on success, rolls back on failure, and closes
its connection. Do not nest decorated operations: they share the cached
connection. Initialization uses SQLite's `executescript` transaction semantics.

All SQL columns are authoritative. JSON sections use TEXT with `json_valid`
checks and object/array root checks as appropriate. Python readers return
decoded dictionaries/lists through typed models. SQLite has no native JSON
column type: `sqlite3 -json` still quotes TEXT values; use `json_extract` for
queries or the computed JSON records in the `applications` view for export.
`basis_for_resumes` accepts any valid JSON value, including quoted JSON strings.

## Copy one job into a test database

```sh
bash scripts/copy_one_job.sh
```

The source is `$DB_PATH` if set, otherwise
`$HOME/.local/share/resumes/records.sqlite3`. It must have the current migrated
schema. The script opens it read-only, selects one job ordered by ID, and pipes
its JSON into `DB_PATH=.../test.db uv run jobs put`. The destination is always
`test.db` in this repository. Source and destination must differ; existing
destination records are not deleted or overwritten.

To select a different source:

```sh
DB_PATH="$HOME/backup.sqlite3" bash scripts/copy_one_job.sh
```

## Migrating the legacy CLI database

Stop all CLI commands and other database writers, then run this once with the
explicit path to your existing database:

```sh
python scripts/migrate_db.py /path/to/_records.sqlite3
```

The standalone script uses only Python's standard library. It rebuilds `jobs`
and `resumes` using its frozen `scripts/schema_v1.sql`, adds defaults for future inserts,
and installs the timestamp-update triggers and applications view. Existing
row IDs, nulls, dates, outcomes, nested JSON encodings, and `item_json` text are
preserved exactly; there is no backfill or metadata synchronization.

A SQLite backup (including committed WAL data) is created before changes at
`DATABASE.before-ats-db.sqlite3`. Use `--backup /path/to/backup.sqlite3` to
choose another location. Existing backups are never overwritten. Rebuilding,
copying, and validation occur in one transaction; failures roll back and retain
the completed backup. Running against the already-v1 schema is a no-op.
Unsupported column layouts, integrity failures, and existing orphaned foreign
keys abort explicitly without deleting or repairing records.
Older databases without the `resumes.job` foreign key are supported: the
constraint is added only after verifying that every non-null job reference
exists. Different existing foreign-key definitions remain unsupported.

Custom indexes and triggers on these tables are retained, except for the
timestamp triggers supplied by the target schema. Other tables and custom
views are retained. Foreign-key enforcement remains a per-connection setting:
the new Python helpers enable it, while older tools must enable it themselves.
The first migration retains `item_json` for legacy CLI compatibility.

## Second migration: remove item_json

Stop database writers and run:

```sh
python scripts/migrate_remove_item_json.py /path/to/_records.sqlite3
```

This rebuilds the tables with the current schema, removes `item_json`, and adds
JSON validation constraints to the individual section columns. It preserves
every other stored column and its exact encoding. **Fields stored only in
`item_json` are deliberately discarded.** The full original is backed up to
`DATABASE.before-remove-item-json.sqlite3`; `--backup` selects another path.
The backup is never overwritten, failures roll back, and reruns are a no-op.
Invalid existing JSON or custom objects that depend on the removed column
cause an explicit failure, not automatic data repair.

The applications view now computes its JSON records from SQL columns, without
storing duplicates. Existing legacy skills/award shapes are decoded by the
shared adapters. Old CLI commands that read/write `item_json` are **not compatible
with the second migration**; use the updated Python helpers instead. The
first migration script remains frozen and cannot downgrade the second schema.

Run the focused tests using the project's Python environment:

```sh
python -m unittest discover -s tests -v
```

The integration suite creates and seeds real SQLite files in temporary folders
and runs the installed `jobs`/`resumes` entry points via `uv`, with synchronization
disabled so tests do not install or update dependencies. It covers inserts,
JSON reads, deletes, defaults, validation failures, duplicate IDs, foreign keys,
the applications view, and the actual `copy_one_job.sh` stdin pipeline. The
copy script is staged in a temporary repository so its `test.db` is temporary
too. Both default-path and `DB_PATH` sources are tested without reading personal
databases. An existing project `.venv` with the installed CLI and `uv` on PATH
are required.

Run only those tests:

```sh
python -m unittest discover -s tests -p test_cli_integration.py -v
```

There is no update helper or CLI update command yet; the suite covers all
currently implemented create/read/delete operations.
